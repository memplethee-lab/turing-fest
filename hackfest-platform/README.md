# Hackfest Platform

A small "Capture-the-Patch" style exploit-and-patch platform for a 1-day event.
Teams register, get challenges (vulnerable code + a briefing), submit fixed
files, and a judge worker grades each submission in an isolated container
against a hidden test suite. A live leaderboard updates as teams solve.

## Quick start

```bash
cp .env.example .env            # edit with real secrets (Neon DATABASE_URL etc.)
python scripts/apply_schema.py  # create tables in Neon (once, idempotent)
docker build -t hackfest/webhook-replay:latest ./challenges/webhook-replay
docker compose up --build
```

API comes up at `http://localhost/api`, leaderboard UI at `http://localhost/`,
and the participant code-editor workspace at `http://localhost/workspace.html`.

## Deploying to Render

`render.yaml` is a Render Blueprint that deploys the api, frontend, and Redis
to Render (free plans). **Postgres is external: Neon** - one shared database
for local compose, Render, and the worker (no Render Postgres instance, no
local db container).

**The judge worker is deliberately not in
the Blueprint**: it grades submissions by launching sibling Docker containers,
and Render managed services have no Docker daemon. Run the worker on any host
that does have Docker, against the same Neon database + Render's Redis.

One-time setup:

1. Push this repo to GitHub. The Blueprint (`hackfest-platform/render.yaml`)
   sets `rootDir: hackfest-platform` on each service, so `dockerfilePath` and
   `dockerContext` resolve inside that subdirectory even from the repo root.
2. In Render, create a **Blueprint** from that repo. It will provision:
   - `hackfest-api` (Docker, `api/Dockerfile.render`) with `/health` checks
   - `hackfest-frontend` (Docker, `frontend/Dockerfile.render`) — nginx
     serving the pages and proxying `/api/` to the api, same as locally
   - `hackfest-redis` (free Key Value, `noeviction` so queue/leaderboard keys
     are never evicted)
3. When the sync prompts for secrets, enter the real `ADMIN_PASSWORD` and the
   **Neon `DATABASE_URL`** (keep `?sslmode=require` and `channel_binding=require`).
   `JWT_SECRET`/`FLAG_SECRET` are auto-generated by the Blueprint.
4. The schema is applied automatically — the api runs `db/schema.sql`
   against Neon at startup (idempotent; free-tier services can't run a
   `preDeployCommand`, so the bootstrap lives in `api/app/bootstrap.py`).

Free web services **sleep after ~15 minutes without traffic**; the first
request then takes ~30–60s to cold-start. For a live event with ~50 teams
poking the leaderboard, upgrade both web services to `0.5c-512mb` (change
`plan: free` in `render.yaml`).

Running the judge worker (outside Render):

1. On a Docker-capable host you trust (the Docker socket mount is a real
   privilege — see Security notes), check out the repo and:
   ```bash
   cp .env.worker.example .env.worker   # Neon DATABASE_URL + Render Redis external URL
   docker build -t hackfest/webhook-replay:latest ./challenges/webhook-replay
   docker compose -f docker-compose.worker.yml --env-file .env.worker up -d --scale worker=3
   ```
2. The Neon string is the same one used everywhere (pooled endpoint is
   fine for a one-day event; keep `sslmode=require`). For Redis: Key Value →
   enable **external connections** → the `rediss://` URL with its auth token.
3. The Blueprint leaves the Key Value IP allow-list open to everywhere
   so the external worker can connect; **tighten it to the worker host's
   IP** once you know it.

Submissions queue up in Redis and show `queued` until a worker picks them
up — the platform is fully functional for browsing/registering even before
the worker host is up.

## Admin UI

Visit `http://localhost/admin.html`, log in with an admin account
(username + password). The first login ever is bootstrapped from
`ADMIN_PASSWORD` (set in `.env`) as user `admin`; after that, accounts live
in the DB and are managed on the Admins tab.

- **Events** — create an event (name, start/end time in your browser's local
  time, converted to UTC on submit), or edit an existing event's start/end
  mid-event (e.g. extending the deadline), and manually freeze the
  leaderboard.
- **Challenges** — add a challenge to the selected event: slug (must match
  the `challenges/<slug>/` directory and built image tag), title, points,
  time-bonus budget, which filenames teams may submit, and the briefing text
  shown to teams. **Edit** any of these mid-event (`PATCH /api/admin/challenges/{id}`
  — already-awarded solves keep the points granted at solve time), or delete
  a challenge (existing submissions for it are kept). The form also carries
  the teams' **starting file contents** (`=== filename ===` sections, stored
  in `challenge_files` and served to the workspace editor via
  `GET /api/challenges/{slug}/start`).
- **Teams & Scores** — live-ish table of every team's total points and solve
  count for the selected event, plus a CSV export button.
- **Submissions** — a monitor of recent submissions with status (queued /
  running / passed / failed / error), filterable by status. An `error`
  status (worker crashed, Docker hiccuped, etc. — not a real pass/fail
  grading result) gets a **regrade** button that re-queues it.
- **Admins** — add/remove per-admin accounts. Each login issues its own
  token, so removing a departed organizer's account stops them at their
  next login. The last remaining account can't be deleted, and you can't
  delete your own while others exist.

Everything the admin UI does goes through `/api/admin/*`, so you can script
event setup instead of clicking through the UI if you prefer — e.g. to seed
an event from a file listing all your challenges at once.

### Seeding directly with SQL (optional, instead of the UI)

```sql
INSERT INTO events (name, start_at, end_at)
VALUES ('My Hackfest', '2026-11-01T09:00:00Z', '2026-11-01T17:00:00Z')
RETURNING id;

-- then, using that event's id:
INSERT INTO challenges (event_id, slug, title, points, time_bonus_points, editable_files, briefing_md)
VALUES (
  '<event_id>', 'webhook-replay', 'Webhook Replay & Staleness', 100, 30,
  ARRAY['Freshness.ts', 'NonceStore.ts'],
  'Fix Freshness.ts and NonceStore.ts so a verified webhook is acted on exactly once, and only while fresh.'
);
```

Teams then register with that `event_id` via `POST /api/teams/register`.

### Participant accounts (email-first)

Participants are invited by email — the admin pastes the emails into the
roster (see "Closed registration" below). A participant then opens
`/workspace.html` and uses that same email plus a password of their choosing:

- `POST /api/users/signup` — `{email, password, display_name?}`. Creates the
  account in the best event to play in right now (running before upcoming before
  ended; if two are equally live, the one whose roster names them wins), claims
  that event's invite when its roster has one for them, and gives them a
  **personal team** named after their
  display name (default: the email's first half). Returns the token plus the
  `events` list for the picker — they can switch to any other event immediately.
- `POST /api/users/login` — `{login: <email>, password}` → user token (scoped to
  their running event, or the next to start, or the most recent one to finish)
  plus the same `events` list. Legacy
  `{username, password}` still works. Answers 404 when no account exists yet
  and 401 on a wrong password, so the UI can tell "create your account" from
  "wrong password".
- `GET /api/users/events` — everything the participant can reach, the running
  event first, then upcoming, then past ones. This is what the workspace picker
  lists; nobody types an event id.
- `POST /api/users/events/{event_id}/enter` — choose an event. Reuses the
  account and team they already have there, otherwise claims the invite (if this
  event has one for them) and creates the personal team, then returns a token
  scoped to that event. 403 only when the event is closed **and** their email is
  on no roster anywhere.
- `GET /api/users/me` — who I am, my team, my event, and my teammates.

**The invite belongs to the person, not to one event.** An email on any roster
is a participant of the whole hackfest: they see every event — other events'
closed ones included — and may enter any of them. Being named on a specific
event's roster only decides whose invite gets *claimed* and which event is
offered first. A closed event stays invisible to an email that appears on no
roster at all, which is what keeps a private event private.

An account is one **(email, event)** pair: entering two events gives a personal
team in each, so points and rank are per event. `users.event_id` is that
membership, and the old global `UNIQUE(username)` is now
`UNIQUE (lower(email), event_id)` — same email, different events is fine. Past
events are listed for their results; the API refuses submissions once `end_at`
has passed, so the workspace links those rows to their leaderboard instead of
the editor.

Because every participant gets a personal team, the leaderboard (which is
scored per team) lists one row per participant by default. Group play is
optional and unchanged: `POST /api/teams/register` creates a shared team, and
`POST /api/users/register` (`{event_id, team_name, team_password, username,
password}`) joins one — members of a shared team score and rank together, and
the leaderboard marks those rows "team of N".

A user token carries the same `team_id`/`event_id` claims as the team token,
so `POST /api/submissions` and the submission-status route accept either —
rate limits stay **per team** either way, so one eager member can't burn the
team's cooldown faster than the team itself could.

### Closed registration (invite roster)

By default registration is **open** — anyone with the event id can create a
team. For closed events:

1. **Admin → Events → Participant roster**: paste the invited emails (one per
   line, `POST /api/admin/events/{id}/roster`; duplicates and malformed lines
   are reported back). The table shows each email as `unused`,
   `team: <name>`, or registered-user status.
2. Flip **Registration mode** to `closed`
   (`PATCH /api/admin/events/{id}` with `{registration_mode: "closed"}`).
3. From then on **every** registration path demands a roster email:
   - `POST /api/users/signup` — the normal path: the email must be on some
     event's roster (see "the invite belongs to the person" above). Signup
     claims this event's invite atomically and creates a personal team, so there
     is nothing else for the participant to look up.
     `POST /api/users/events/{id}/enter` applies the same rule when a returning
     participant opens another event; if that event's roster doesn't name them,
     they simply get a personal team with no invite to claim.
   - `POST /api/teams/register` — `{..., email}` claims one unused invite
     atomically (two parties racing for the same email get a single winner;
     the loser gets a 403).
   - `POST /api/users/register` — `{..., email}` must be **unused or already
     claimed by that same team** (so a captain can register their own personal
     account with the email they used to create the team), and no two users
     in an event can bind the same email.
4. Deleting a claimed entry is blocked (claims are audit history); only
   `unused` entries are removable. Teams/users registered before the switch
   stay valid — closing registration never locks existing accounts out.

Emails are normalized (trimmed, lowercased, `mailto:`-stripped) on both the
bulk paste and at claim time, so `Person@School.edu` matches its roster twin.

## Participant workspace (side-by-side editor)

`http://localhost/workspace.html` (or `/workspace.html` on Render) is the
team-facing web UI:

```
┌───────────────────────────────┬───────────────────────────────────┐
│ LEFT — the challenge          │ RIGHT — the editor (CodeMirror)   │
│ briefing, rendered markdown   │ one tab per editable file         │
│ last submission status +      │ [Submit] [Reset ⚠] · Ctrl+Enter   │
│ per-check pass/fail list      │ autosaves drafts to the server    │
└───────────────────────────────┴───────────────────────────────────┘
```

- **Sign in with the email the organizer registered, then pick your event.**
  The page posts to `/api/users/signup` on first visit or `/api/users/login`
  afterwards, then lists every event you can reach (`GET /api/users/events`)
  with the active one on top and past events below, each linked to its
  leaderboard. Choosing one calls `POST /api/users/events/{id}/enter` — no event
  id is ever typed. **Events** in the header reopens the picker to switch. The
  token is scoped to the chosen event and lives in `localStorage`; the page sets
  a strict `Content-Security-Policy` meta so a stray script can't speak to other
  origins.
- **The leaderboard has an Event selector** (`GET /api/events`, running first),
  so past results stay browsable after an event ends instead of the page being
  pinned to whatever is live. `?event_id=` still wins if you arrive from the
  workspace or a picker link.
- **The editor opens with the seeded starting files.** Admins paste the per-file
  starting contents in the Challenge form (`=== Freshness.ts ===` style
  `=== filename ===` sections); the api stores them in the `challenge_files`
  table and serves them via `GET /api/challenges/{slug}/start`. Only
  `editable_files` are ever stored there — hidden test files must never be
  seeded. The vulnerable files also live in the challenge image; the DB seed
  is what teams see, so keep them in sync when you rework a lab.
- **Draft autosave** (`PUT /api/challenges/{slug}/draft/{file}`, 1.5s after the
  last keystroke, plus on submit/reset): per team, per file, expires in a week.
  Drafts are not submissions — no rate limit, no grading. They also give
  organizers an evidentiary trail if a result is disputed.
- **Reset file** re-pulls the pristine file from the server and re-saves the
  draft — mirroring the "reset = fresh from the image" rule.
- **Submit** posts exactly what the current buffers hold via the normal
  `POST /api/submissions` shape; the page then polls the submission status and
  shows the per-check results (check names only — never test contents).
- The **event timer** is cosmetic (server times from `GET /api/challenges`, your
  browser's clock for the countdown); all enforcement remains server-side.

### Anti-cheat: what stops copying

Everything graded here is *server-verified*, never browser-observed:

1. **Hidden tests never leave the image** — grading runs in a network-disabled
   container; teams only ever see pass/fail per named check.
2. **Token-shingle similarity, cross-team only** — the admin
   **Coincidences** tab (`GET /api/admin/events/{id}/similarity`) fingerprints
   every submission (lowercase alphanumeric token stream → 8-gram shingles →
   Jaccard), which is robust to whitespace/comment reflowing and only compares
   *different* teams on the *same* challenge+file. It surfaces evidence for
   human review, it never auto-disqualifies. Same-team pairs are skipped by
   design; 0.7–0.8 is generic-idiom territory, >0.9 is copy-paste territory.
3. **Per-team cooldown + hourly cap** — the same rate limit that protects the
   judge queue also blunts rapid-fire answer trading.
4. **Exploit phase stays local.** Participants run the vulnerable app via
   `docker compose` on their own machine when a briefing says to explore; the
   platform never executes participant code outside the judge container, and
   the api exposes no exec endpoint — it can't be used as a compute service.
5. **No flag guessing possible** — there are no flags to guess at all; grading
   *is* the challenge.
   What this means for briefings: don't design graded checks around a secret
   value teams could copy between each other post-hoc (e.g. "change the API key
   to X") — the checks must test behavior, not a coordinator-distributed
   string. The hidden tests exist precisely so answers can't be shared as
   text; keep it that way.
6. **Editor-level "anti-copy" UI features are deliberately omitted** —
   devtools bypass them and they only punish honest teams; the Coincidences
   report catches the same offense server-side.

## How grading works

1. Team calls `POST /api/submissions` with their edited file contents.
2. API checks the event is currently `running` (server clock only — never
   trust the browser), queues the submission in Redis, returns immediately.
3. A judge worker pops it, starts a **network-disabled**, memory/CPU/PID
   -limited container from the challenge's image, copies the team's files
   into the editable directory, execs `verify.sh`, and tears the container
   down unconditionally afterward.
4. `verify.sh` runs the hidden test suite and prints one JSON line:
   `{"passed": bool, "checks": [...]}`.
5. On a pass, the worker records the first solve (resubmits don't re-score),
   computes points + a decaying time bonus, and pushes the new total onto
   the Redis leaderboard sorted set.
6. The frontend leaderboard page subscribes to an SSE stream and re-renders
   every couple seconds.

## Adding another challenge

1. `challenges/<slug>/` with the same shape as `webhook-replay/`:
   - `Dockerfile` that builds an image containing the vulnerable app under
     some fixed `editable_dir`
   - `tests/hidden_tests.*` — the real grading logic, never shipped to teams
   - `verify.sh` — runs the hidden tests, prints the one JSON result line
   - `meta.yaml` — slug, image tag, editable_dir, editable_files, verify_cmd, points
   - `solutions/` (optional, organizer-only) — a known-good fix per editable
     file. Kept outside `app/` so it is never baked into the team-facing
     image. Use it to sanity-check a new challenge before the event: the
     vulnerable files must FAIL `hidden_tests`, and the solution must PASS.
2. `docker build -t hackfest/<slug>:latest ./challenges/<slug>`
3. Insert a row into `challenges` pointing at it, and seed one
   `challenge_files` row per editable file (the workspace editor serves these
   as the teams' starting content):
   ```sql
   INSERT INTO challenge_files (challenge_id, filename, content)
   VALUES
     ('<challenge_id>', 'Freshness.ts', '<full file content>'),
     ('<challenge_id>', 'NonceStore.ts', '<full file content>');
   ```
   (Or paste the `=== filename ===` sections into the admin Challenge form —
   same rows, created through `POST/PATCH /api/admin/challenges`.)

Porting one of the existing patch-lab challenges (SSRF, deserialization,
IDOR, etc.) into this shape is mostly: move the vulnerable file(s) into
`app/editable/`, turn the lab's `verify` logic into `hidden_tests.*`, and
write the Dockerfile for that language's runtime.

## Security notes (read before running a real event)

- **Isolation is the whole game.** The judge container runs `network_disabled`,
  capped memory/CPU, `pids_limit`, `cap_drop: ALL`, `no-new-privileges`, and
  a hard wall-clock timeout, then is force-removed in a `finally` block even
  on error. Don't weaken any of these without a specific reason.
- **The worker needs the Docker socket mounted** to launch sibling
  containers. That's a real privilege — the worker process itself should run
  on a host you trust, isolated from anything else sensitive, since anything
  that can talk to that socket can effectively control the host's Docker
  daemon. Don't expose the worker's port/socket beyond the compose network.
- **Flags/results aren't exposed to teams beyond pass/fail per check.** The
  `checks` array returned to the team should describe *what* was checked in
  plain language (as the lab did), never leak the hidden test file contents.
- **Reset should mean "new container from the image," never "restore a file
  in place."** This avoids the exact confusion from the lab session this
  platform is modeled on (`reset` appearing to go back one edit instead of
  to the true original). There is intentionally no in-place file reset here —
  the vulnerable files only ever exist inside the immutable challenge image.
- **Submission abuse is rate-limited in Redis, per team.** `POST /api/submissions`
  enforces a `SUBMISSION_COOLDOWN_SECONDS` (default 60) cooldown and a
  `SUBMISSIONS_PER_HOUR` (default 20) fixed-window cap, so one team can't
  starve the judge queue for everyone else. Limits are counted only after
  a submission passes validation, and admin `/regrade` bypasses them by
  design. Raise or lower via `.env`.
- **CORS is configured via `ALLOWED_ORIGINS`** (comma-separated, defaults to
  `*`). With the stock nginx setup the frontend is same-origin, so you can
  leave it alone; set it to your real frontend origin if you host the pages
  on a different domain.
- **Registration defaults to open.** For a closed event, paste the invited
  emails into the roster and flip the event's registration mode to `closed`
  — see "Closed registration" above. Personal signup and team registration
  then both require an unclaimed roster email; existing accounts stay valid.
